# Fake Payments

Fake Payments is a small Laravel application for learning and demonstrating a
payment-like checkout flow. A visitor can browse seeded products, submit a
payment form, and trigger a queued verification-code job.

This project **does not charge a card, connect to a bank, or integrate with a
real payment provider**. It is intentionally a local simulation that shows how
controllers, services, models, validation, database records, queues, and a
React interface can work together.

## What the project demonstrates

- A Laravel 13 backend running on PHP 8.3 or newer.
- An Inertia.js 3 application that renders React pages without a separate API.
- Product browsing backed by Eloquent models and SQLite.
- Payment creation with request validation and business-rule validation.
- A service layer for product lookup and payment creation.
- A queued job that simulates sending a payment verification code.
- Database-backed sessions, cache, and queues for local development.
- Tailwind CSS 4 and DaisyUI for the interface.
- Pest tests and Vite for frontend asset compilation.

## How the application works

The main user journey is:

```text
Home
  -> Register
  -> Login
  -> Product list
  -> Product details and payment form
  -> PaymentController@store
  -> StorePaymentRequest validation
  -> PaymentService business rules
  -> Payment database record
  -> SendVerificationCode queued job
  -> Redirect back to the product
```

### 1. Authentication pages

`/register` displays the registration form and creates a user with a hashed
password. `/login` checks the supplied credentials and regenerates the session
after a successful login.

The authentication implementation is intentionally lightweight and is included
to support the demonstration flow. It is not intended to be a complete
production authentication system yet.

### 2. Product browsing

`ProductController@index` asks `ProductService` for all products and returns the
Inertia `Products` page. Selecting a product calls
`ProductController@show`, which loads the product and returns the
`ShowProduct` page.

Products have:

- `name`
- `description`
- `price`
- optional `image`

The default database seeder creates four products using `ProductFactory`.
Product images are remote Unsplash URLs generated by the factory.

### 3. Payment submission

The checkout form submits to `POST /payments`. The request passes through
`StorePaymentRequest`, which checks that:

- the product exists;
- the customer name is present;
- the phone number is present and within the configured length;
- the amount is numeric and non-negative.

`PaymentService` then applies the application-specific rules:

- required payment fields must be present;
- the phone number must match the expected international format;
- the submitted amount must be at least the product price.

If validation succeeds, a `Payment` record is created with the selected
product, customer name, phone number, and amount.

### 4. Verification job and queue

After a payment is stored, `PaymentController@store` dispatches
`SendVerificationCode`:

```php
SendVerificationCode::dispatch($user, $payment, $payment->product);
```

The job implements Laravel's `ShouldQueue` contract. In the current prototype it
does not send an SMS or email. Instead, it:

1. builds a demonstration message;
2. waits five seconds to imitate an external delivery service;
3. dumps the message for inspection.

The default local queue connection is `database`, so pending jobs are stored in
the `jobs` table. Run a worker when you want to observe the job asynchronously:

```bash
php artisan queue:work
```

For automated tests, `phpunit.xml` changes the queue connection to `sync`, so
jobs run immediately and do not require a separate worker.

## Important backend components

### Controllers

- `AuthController` handles registration and login form submissions.
- `ProductController` loads product collections and individual products.
- `PaymentController` displays the payment form, validates submissions through
  the request class, creates payments through `PaymentService`, and dispatches
  the verification job.

Controllers are intentionally thin: they coordinate the request and response
while reusable payment and product behavior lives in services.

### Services

- `ProductService` provides product listing and lookup methods.
- `PaymentService` creates payments and contains the phone and amount checks
  that are specific to this application's business flow.

### Models and database relationships

The `products` table stores sellable products. The `payments` table stores a
payment attempt and references a product through `product_id` with a cascading
foreign key.

The main data relationship is:

```text
Product (1) ────────< Payment (many)
```

Users are stored in Laravel's standard `users` table and are used by the
authentication flow and verification job.

### Form requests and policies

`StorePaymentRequest` is the active payment validation boundary.
`StoreProductRequest`, update request classes, and the product/payment policy
classes are present as extension points, but their CRUD and authorization
behavior is not fully implemented yet.

## Routes

| Method | URI | Purpose |
| --- | --- | --- |
| GET | `/` | Home page |
| GET/POST | `/register` | Registration form and submission |
| GET/POST | `/login` | Login form and submission |
| POST | `/logout` | Declared logout route |
| GET | `/products` | Product listing |
| GET | `/products/{product}` | Product details and checkout form |
| POST | `/payments` | Create a payment and dispatch verification |

The resource routes for products and payments are declared broadly, but only
listing, showing, creating, and storing are currently meaningful in the
controllers. Product administration, payment viewing/editing/deleting, and
complete authorization are future work.

## Local setup

### Requirements

- PHP 8.3 or newer
- Composer
- Node.js and npm
- SQLite with PHP's SQLite extension

### Installation

From the repository root:

```bash
composer run setup
```

The setup script installs PHP dependencies, creates `.env`, generates the
application key, runs migrations, installs JavaScript dependencies, and builds
frontend assets.

If you prefer to run the steps separately:

```bash
composer install
copy .env.example .env
php artisan key:generate
php artisan migrate
npm install
npm run build
```

The default `.env.example` configuration uses:

- SQLite for the database;
- database sessions;
- database cache;
- database queues;
- the log mailer, so no external email credentials are required.

### Seed sample products

The default `DatabaseSeeder` creates four products:

```bash
php artisan db:seed
```

To rebuild the local database and seed it in one command:

```bash
php artisan migrate:fresh --seed
```

### Run the application

Start the Laravel development server:

```bash
php artisan serve
```

In a second terminal, run the frontend watcher if you are actively changing
React or CSS:

```bash
npm run dev
```

If you want the queued verification job to run asynchronously, start a third
terminal:

```bash
php artisan queue:work
```

Then open `http://localhost:8000`.

## Testing and code quality

Run the test suite with:

The current test suite contains a basic home-page feature test and a unit

Build production frontend assets with:

```bash

```

## Services and external integrations

The project is designed to run locally without third-party credentials:

- **Database:** SQLite by default.
- **Mail:** Laravel's `log` mailer; messages are written to the application log
  rather than sent.
- **Queue:** Laravel's database driver; jobs are stored in the `jobs` table.
- **Images:** Product seed data uses remote Unsplash image URLs.
- **Broadcasting and storage:** Laravel defaults are configured for local
  development.

The verification job is the natural place to add a real mail, SMS, or payment
provider later. A production integration should add provider credentials via
environment variables, handle provider failures and retries, and never treat
this demo's fixed verification code as secure.

## Current scope and limitations

This repository is a teaching prototype. In particular:

- no real money is transferred;
- no card, bank, wallet, or payment gateway is contacted;
- the verification code is fixed and only dumped for demonstration;
- authentication and route protection are minimal;
- CRUD controller methods and policies are incomplete;
- the test suite is intentionally small;
- there is no production payment reconciliation, webhook handling, or fraud
  protection.

These limitations are deliberate so the code remains easy to explore. They
also define the next areas to improve before considering a production-ready
payment system.
